## Clarifications

### Session 2026-03-10

- Q: 시그널 → 주문 실행 시 사용자 확인이 필수인가? (자동 제출 vs 승인 후 제출 vs 수동만) → A: 시그널로 주문 초안만 생성하고, 사용자가 확인·수정 후 제출(Option B).
- Q: 사용자당 포트폴리오 단위(1인 1개 vs 복수 vs 팀 공유) → A: 1인 복수 포트폴리오. 단, 주문 실행에 연동되는 포트폴리오는 1개만(실행용 포트폴리오를 사용자가 선택).
- Q: 이벤트·시그널 처리 지연·대시보드 로드 시간 목표 → A: 구체적 목표 명시. 뉴스 수집 후 이벤트 목록 반영 5분 이내, 대시보드 초기 로드 3초 이내.
- Q: 데이터·사용자 규모 가정 → A: 스펙에 대략적 가정 명시. 일일 뉴스 약 1만 건·이벤트 약 5천 건 수준, 동시 사용자 약 100명 수준.
- Q: 알림 전달 채널(인앱 vs 이메일 vs 푸시) → A: 인앱만. 알림은 대시보드·앱 내 알림 영역에만 표시.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 뉴스·정책에서 이벤트 확인 (Priority: P1)

투자자는 뉴스, 정책 발표, 경제 지표 등 텍스트/데이터가 수집·구조화된 이벤트로 표시되어, 시장에서 무슨 일이 일어났는지 빠르게 파악할 수 있다.

**Why this priority**: 정보 수집부터 이벤트 추출까지가 플랫폼의 입력 단계이며, 이후 자산 영향·시그널·주문의 기반이 됨.

**Independent Test**: 뉴스/정책 텍스트를 입력하면 이벤트 유형·관련 국가·영향·발생 시점이 구조화되어 나오는지 확인할 수 있으며, 이 단계만으로도 "무슨 이벤트가 있었는지" 가치를 제공함.

**Acceptance Scenarios**:

1. **Given** 뉴스·정책·경제 리포트가 수집됨, **When** 사용자가 이벤트 목록을 조회함, **Then** 이벤트 유형·국가·관련 자산·강도·시점이 구조화되어 표시됨
2. **Given** 새 뉴스가 도착함, **When** 시스템이 텍스트를 분석함, **Then** 해당 텍스트에서 추출된 이벤트가 저장되고 목록에 반영됨
3. **Given** 이벤트 목록이 있음, **When** 사용자가 특정 이벤트를 선택함, **Then** 해당 이벤트의 출처(뉴스/정책 등)와 추출된 속성을 확인할 수 있음

---

### User Story 2 - 이벤트가 자산에 미치는 영향 보기 (Priority: P1)

투자자는 특정 이벤트(예: 금리 인상, 지정학 이슈)가 주식·채권·외환·금·원자재 등 어떤 자산에 어떤 방향으로 영향을 주는지 확인할 수 있다.

**Why this priority**: 이벤트만 보는 것에서 한 단계 나아가 "어디에 어떻게 투자할지" 판단의 직접적인 입력이 됨.

**Independent Test**: 이벤트를 선택하면 영향받는 자산·영향 방향(상승/하락)·영향 강도가 표시되는지 확인할 수 있으며, 이 기능만으로도 자산별 영향 분석 가치를 제공함.

**Acceptance Scenarios**:

1. **Given** 이벤트가 존재함, **When** 사용자가 해당 이벤트의 자산 영향을 조회함, **Then** 영향받는 자산 목록과 방향(상승/하락 등)·강도가 표시됨
2. **Given** 자산 관계·거시경제 모델이 반영됨, **When** 새 이벤트가 분석됨, **Then** 해당 이벤트에 대한 자산 영향 결과가 생성·저장됨
3. **Given** 여러 자산에 영향이 있음, **When** 사용자가 영향 목록을 본다, **Then** 자산별로 정렬·필터하여 볼 수 있음

---

### User Story 3 - 투자 시그널 확인 및 활용 (Priority: P1)

투자자는 이벤트·자산 영향 분석 결과를 바탕으로 생성된 투자 시그널(매수/매도/축소/헤지 등)을 보고, 신뢰도·사유·연관 이벤트를 확인한 뒤 의사결정에 활용할 수 있다.

**Why this priority**: 이벤트→영향→행동으로 이어지는 파이프라인의 "행동 제안" 단계로, 플랫폼의 핵심 가치인 "정보→투자 행동 연결"을 완성함.

**Independent Test**: 이벤트·자산 영향이 있을 때 시그널이 생성되고, 사용자가 시그널 목록에서 자산·방향·신뢰도·사유를 확인할 수 있으면 됨. 시그널만으로도 "무엇을 할지" 제안 가치를 제공함.

**Acceptance Scenarios**:

1. **Given** 이벤트와 자산 영향 분석이 있음, **When** 시스템이 시그널을 생성함, **Then** 자산·방향·신뢰도·사유·연관 이벤트·시점이 포함된 시그널이 저장됨
2. **Given** 시그널 목록이 있음, **When** 사용자가 시그널을 조회함, **Then** 자산별·시간순으로 필터·정렬하여 볼 수 있음
3. **Given** 사용자가 시그널을 선택함, **When** 상세를 조회함, **Then** 해당 시그널을 만든 이벤트·자산 영향 근거를 추적할 수 있음

---

### User Story 4 - 포트폴리오 조회 및 자산 배분 관리 (Priority: P2)

투자자는 복수의 포트폴리오를 생성·전환하며, 각 포트폴리오별로 보유 자산·비중·평가·리스크 지표·성과를 보고 리밸런싱 목표를 설정할 수 있다. 주문 실행(브로커·거래소 연동)에 사용되는 포트폴리오는 사용자가 하나만 지정하며, 그 포트폴리오 기준으로만 주문·포지션이 반영된다.

**Why this priority**: 시그널을 "어디에 얼마나 걸었는지" 관리하는 단계로, 실행 전 의사결정과 리스크 관리에 필요함.

**Independent Test**: 포트폴리오·포지션·총 평가·자산 비중·성과가 조회 가능하고, 리밸런싱 목표를 설정하면 목표 대비 현재 비중이 표시되는지로 검증 가능함.

**Acceptance Scenarios**:

1. **Given** 사용자에게 포트폴리오가 있음, **When** 포트폴리오 목록·전환을 조회함, **Then** 보유한 복수 포트폴리오 중 선택해 해당 포트폴리오의 자산·수량·평가·비중·리스크 지표가 표시됨
2. **Given** 사용자가 복수 포트폴리오를 보유함, **When** 주문 실행에 사용할 포트폴리오를 하나 지정함, **Then** 이후 주문·포지션 반영은 그 포트폴리오에만 적용됨
3. **Given** 포트폴리오가 있음, **When** 성과를 조회함, **Then** 기간별 수익률·성과 요약을 확인할 수 있음
4. **Given** 사용자가 목표 자산 배분을 설정함, **When** 현재 포트폴리오와 비교함, **Then** 목표 대비 현재 비중·리밸런싱 필요량이 표시됨

---

### User Story 5 - 시그널 기반 주문 실행 (Priority: P2)

투자자는 시그널을 바탕으로 시스템이 생성한 주문 초안(시장가·지정가·스탑 등)을 확인·수정한 뒤 직접 제출하며, 브로커·거래소 연동으로 상태 추적·포지션 반영까지 할 수 있다. 포트폴리오 결정에 따른 주문도 사용자가 생성·제출한다.

**Why this priority**: "정보→이벤트→영향→시그널"을 실제 거래로 연결하는 마지막 단계로, 플랫폼의 실행 가치를 완성함.

**Independent Test**: 시그널 또는 사용자 입력으로 주문을 생성·제출하고, 주문 상태·포지션 변경이 조회되면 됨. 외부 브로커/거래소 연동은 연동 가능한 한 개수로 검증 가능함.

**Acceptance Scenarios**:

1. **Given** 시그널이 있음, **When** 사용자가 해당 시그널에 대해 주문 초안 생성 요청함, **Then** 시스템이 주문 유형·자산·수량·가격(해당 시) 초안을 생성하고 사용자에게 확인·수정 화면을 제공함
2. **Given** 주문 초안이 있음, **When** 사용자가 내용을 확인·수정 후 제출함, **Then** 주문이 브로커·거래소로 전송되고 상태가 기록됨
3. **Given** 주문이 제출됨, **When** 사용자가 주문 상태를 조회함, **Then** 대기·체결·부분체결·취소 등 상태를 확인할 수 있음
4. **Given** 주문이 체결됨, **When** 포트폴리오를 조회함, **Then** 해당 자산 포지션·평가가 반영됨

---

### User Story 6 - 대시보드에서 이벤트·시그널·포트폴리오 한눈에 보기 (Priority: P2)

투자자는 한 화면(대시보드)에서 최근 이벤트·생성된 시그널·포트폴리오 요약·알림을 동시에 보고, 필요한 항목을 클릭해 상세로 이동할 수 있다.

**Why this priority**: 일일 사용 시 진입점이 되며, 이벤트→시그널→포트폴리오 흐름을 한곳에서 따라갈 수 있게 함.

**Independent Test**: 대시보드 접속 시 이벤트·시그널·포트폴리오 요약·알림이 표시되고, 항목 클릭 시 해당 상세 화면으로 이동하면 됨.

**Acceptance Scenarios**:

1. **Given** 사용자가 로그인함, **When** 대시보드를 연다, **Then** 최근 이벤트·시그널·포트폴리오 요약이 한 화면에 표시됨
2. **Given** 대시보드에 항목이 있음, **When** 사용자가 이벤트/시그널/포지션 항목을 클릭함, **Then** 해당 상세 화면으로 이동함
3. **Given** 중요한 이벤트·시그널·리스크 알림이 있음, **When** 사용자가 대시보드를 본다, **Then** 알림·요약으로 그 내용을 인지할 수 있음

---

### User Story 7 - 리스크·성과 보고서 생성 (Priority: P3)

투자자는 포트폴리오 성과·리스크 지표·시그널 이력·거래 이력 등을 포함한 보고서를 생성하고, 기간·항목을 선택해 조회할 수 있다.

**Why this priority**: 사후 검토·전략 개선·규제·내부 기록에 필요하나, 핵심 거래 흐름보다는 보조 기능임.

**Independent Test**: 보고서 생성 요청 시 포트폴리오 성과·리스크·시그널·거래 이력이 포함된 보고서가 생성·다운로드 또는 조회 가능하면 됨.

**Acceptance Scenarios**:

1. **Given** 포트폴리오·시그널·거래 이력이 있음, **When** 사용자가 보고서 생성을 요청함, **Then** 지정한 기간의 성과·리스크·시그널·거래 요약이 포함된 보고서가 생성됨
2. **Given** 보고서가 생성됨, **When** 사용자가 조회 또는 내보내기를 요청함, **Then** 화면에서 보거나 파일로 받을 수 있음

---

### Edge Cases

- **데이터 부재**: 뉴스/정책이 없거나 이벤트 추출이 불가한 경우, 사용자에게 "분석할 데이터 없음" 또는 해당 기간 이벤트 없음으로 표시하고, 자산 영향·시그널은 기존 데이터만으로 갱신하거나 보류함.
- **외부 연동 장애**: 브로커·거래소 연동이 불가할 때, 주문 제출 실패를 명확히 표시하고 재시도·취소 옵션을 제공하며, 미체결·부분체결 상태를 정확히 반영함.
- **중복·충돌 이벤트**: 동일 소스에서 유사 이벤트가 중복 추출되거나, 상충하는 이벤트가 동시에 있을 때, 중복은 병합·표시 정리하고, 상충 시 두 이벤트 모두 표시하되 시그널 생성 시 정책(우선순위·가중치)에 따라 일관되게 처리함.
- **시그널·주문 한도**: 사용자 또는 시스템 정책으로 시그널 건수·주문 빈도 제한이 있는 경우, 한도 초과 시 새 시그널/주문 생성 중단 또는 대기 상태를 표시하고, 사용자에게 사유를 안내함.
- **지원 자산 외 상품**: 주문·포지션이 플랫폼이 지원하지 않는 자산을 참조할 때, 해당 항목은 "미지원"으로 표시하고 실행은 차단하며, 지원 자산만 필터하여 보여줄 수 있음.

## Requirements *(mandatory)*

### Functional Requirements

**데이터 수집**
- **FR-001**: 시스템은 뉴스·블로그·정책 발표·정치 발언·경제 지표·시장 데이터·기업 공시 등 정의된 소스에서 데이터를 수집·저장할 수 있어야 한다.
- **FR-002**: 시스템은 수집된 데이터에 대해 출처·시점·유형 등 메타데이터를 부여하고, 정규화된 형태로 보관할 수 있어야 한다.

**이벤트 분석**
- **FR-003**: 시스템은 텍스트 기반 데이터에서 이벤트를 추출하여, 이벤트 유형·관련 국가·행위자·영향 유형·시점·출처·신뢰도 등을 구조화된 형태로 저장할 수 있어야 한다.
- **FR-004**: 사용자는 저장된 이벤트 목록을 조회·필터·정렬할 수 있어야 하며, 이벤트별로 출처(뉴스/정책 등)와 추출된 속성을 확인할 수 있어야 한다.

**자산 영향**
- **FR-005**: 시스템은 이벤트와 자산 간 영향 관계(자산·영향 방향·강도)를 계산하고 저장할 수 있어야 한다.
- **FR-006**: 사용자는 이벤트별·자산별로 영향 결과를 조회할 수 있어야 한다.

**시그널**
- **FR-007**: 시스템은 이벤트·자산 영향 결과를 기반으로 투자 시그널(자산·방향·신뢰도·사유·연관 이벤트·시점)을 생성·저장할 수 있어야 한다.
- **FR-008**: 사용자는 시그널 목록을 조회·필터·정렬하고, 시그널에서 연관 이벤트·자산 영향 근거를 추적할 수 있어야 한다.

**포트폴리오**
- **FR-009**: 사용자는 자신 소유의 복수 포트폴리오를 생성·조회·수정·전환할 수 있어야 하며, 각 포트폴리오는 보유 자산·수량·평가·비중을 가진다.
- **FR-009-1**: 사용자는 주문 실행에 연동할 포트폴리오를 하나만 지정할 수 있어야 한다. 지정된 포트폴리오에 대해서만 주문 제출·포지션 반영이 이루어진다.
- **FR-010**: 시스템은 포트폴리오에 대해 리스크 지표·성과(기간별 수익률 등)를 계산하고 사용자에게 표시할 수 있어야 한다.
- **FR-011**: 사용자는 포트폴리오별로 목표 자산 배분을 설정하고, 현재 포트폴리오와 비교하여 리밸런싱 필요량을 확인할 수 있어야 한다.

**주문 실행**
- **FR-012**: 시스템은 시그널을 바탕으로 주문 초안(유형·자산·수량·가격 등)을 생성하여 사용자에게 확인·수정 화면을 제공해야 한다. 사용자는 초안을 수정한 뒤 제출하거나, 시그널 없이 직접 주문을 생성·제출할 수 있어야 한다. 주문 제출은 사용자 동작 후에만 연동된 브로커·거래소로 전송된다.
- **FR-013**: 시스템은 주문 상태(대기·체결·부분체결·취소 등)를 추적하고, 체결 시 실행용으로 지정된 포트폴리오의 포지션에만 반영할 수 있어야 한다.
- **FR-014**: 사용자는 주문 이력·상태를 조회할 수 있어야 한다.

**대시보드·알림**
- **FR-015**: 사용자는 대시보드에서 최근 이벤트·시그널·포트폴리오 요약을 한 화면에 조회할 수 있어야 한다.
- **FR-016**: 시스템은 중요 이벤트·시그널·리스크 알림 등을 사용자에게 전달할 수 있어야 한다. 초기 버전에서는 인앱만 지원하며, 알림은 대시보드 및 앱 내 알림 영역에 표시된다(이메일·푸시는 범위 외).

**보고서**
- **FR-017**: 사용자는 포트폴리오 성과·리스크·시그널 이력·거래 이력을 포함한 보고서를 생성·조회·내보낼 수 있어야 한다.

**지원 자산**
- **FR-018**: 시스템은 최소 주식·암호화폐·외환·채권·금·원자재를 자산 유형으로 지원할 수 있어야 하며, 지원 자산만 시그널·포지션·주문 대상으로 노출·실행할 수 있어야 한다.

### Key Entities

- **Asset**: 투자 대상 자산. 식별자·이름·심볼·자산 유형·통화·거래소·섹터·국가 등 속성.
- **Event**: 뉴스/데이터에서 추출된 시장 이벤트. 유형·국가·행위자·관련 자산·영향 유형·시점·출처·신뢰도 등.
- **News**: 텍스트 기반 정보 소스. 제목·내용·출처·시점·추출된 엔티티 등.
- **Signal**: 투자 행동 제안. 자산·방향(매수/매도/축소/헤지)·신뢰도·사유·연관 이벤트·시점.
- **Order**: 실제 주문. 자산·주문 유형·매수/매도·수량·가격·상태·시점.
- **Position**: 보유 포지션. 자산·수량·진입가·현재가·미실현 손익 등.
- **Portfolio**: 사용자별 자산 구성. 한 사용자가 복수 포트폴리오 보유 가능. 보유 포지션·총 평가·리스크 지표·성과 등. 주문 실행에 연동되는 포트폴리오는 사용자가 1개만 지정.
- **Policy / Indicator**: 정책·경제 지표. 이벤트 또는 자산 영향 분석의 입력으로 사용됨.
- **Company, Country, Currency, Sector**: 엔티티·온톨로지 객체. 이벤트·자산과의 관계(국가·산업 등) 표현에 사용됨.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 대시보드에서 최근 이벤트·시그널·포트폴리오 요약을 1회 로드로 확인할 수 있다. 대시보드 초기 로드는 3초 이내를 목표로 한다.
- **SC-002**: 새로 수집된 뉴스/정책에 대해 이벤트 추출이 수행되고, 수집 완료 후 5분 이내에 해당 이벤트가 목록에 반영되어 사용자가 조회할 수 있다.
- **SC-003**: 이벤트 선택 시 해당 이벤트의 자산 영향 결과를 1회 조회로 확인할 수 있다.
- **SC-004**: 시그널 목록에서 자산·방향·신뢰도·사유를 확인하고, 시그널에서 연관 이벤트로 추적할 수 있다.
- **SC-005**: 사용자가 포트폴리오 조회 시 보유 자산·비중·평가·기간별 성과를 확인할 수 있다.
- **SC-006**: 사용자가 시그널 기반 주문 초안을 확인·수정 후 제출하거나 직접 주문을 생성·제출하고, 주문 상태와 포지션 반영을 조회할 수 있다.
- **SC-007**: 지원 자산(주식·암호화폐·외환·채권·금·원자재)에 대해 시그널·포지션·주문이 일관되게 동작한다.
- **SC-008**: 연동된 브로커·거래소에 장애가 없을 때, 사용자가 제출한 주문이 실행 연동까지 완료되고 상태가 반영된다.
- **SC-009**: 사용자가 요청한 기간의 성과·리스크·시그널·거래 이력을 포함한 보고서를 생성·조회 또는 내보낼 수 있다.

## Assumptions

- **규모 가정**: 초기 버전은 일일 뉴스 약 1만 건, 일일 추출 이벤트 약 5천 건 수준, 동시 사용자 약 100명 수준을 가정한다. 이 범위 내에서 수집·이벤트 추출·시그널 생성·조회가 정상 동작하도록 설계한다.
- 사용자 인증·권한은 플랫폼에 로그인한 개인 투자자·퀀트 개발자를 전제로 하며, 인증 방식은 기존 시스템 또는 업계 일반 관례를 따른다.
- 브로커·거래소 연동은 해당 업체의 공개 API·인증 방식을 사용하며, 초기에는 제한된 브로커/거래소 세트를 지원해도 된다.
- 이벤트 추출·자산 영향·시그널 생성의 구체적 알고리즘(규칙 기반·통계·ML 등)은 구현 단계에서 결정하며, 스펙 단계에서는 "이벤트/영향/시그널이 생성·저장·조회된다"에만 요구사항을 둔다.
- 데이터 보존 기간·개인정보 처리 정책은 법·규정 및 서비스 정책에 따르며, 스펙에서는 "저장·조회 가능" 수준만 요구한다.
- 고빈도 트레이딩·완전 자동 투자(사용자 승인 없이 자동 주문)·초저지연 인프라·자체 브로커 구축은 비목표로, 본 스펙 범위에 포함하지 않는다.
